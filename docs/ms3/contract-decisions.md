## 1. Responses vs saves

Database and HTTP keep attendance and saves separate (Phase 2 `event_responses` + `event_saves`).

| Concern | Frozen rule |
| --- | --- |
| Attendance | `PUT /v1/events/:id/attendance` body `{ "response": "GOING" \| "INTERESTED" \| null }`. `null` deletes the attendance row. |
| Save | `PUT /v1/events/:id/save` body `{ "saved": true \| false }`. Independent of attendance. |
| `viewerResponse` | `"GOING"` \| `"INTERESTED"` \| `null`. Never `"SAVED"`. |
| `viewerSaved` | Boolean. `false` for guests. |

**Intentional frontend difference:** `EventResponseType` in `web/src/types/domain.ts` still includes `"SAVED"`, and `EventView` has no `viewerSaved`. Phase 4 maps the two HTTP fields back into the UI. The API does not pack saves into `viewerResponse`.

Both writes return the updated viewer `EventView`. The viewer must be allowed to view the event; otherwise `NOT_FOUND`.

**Auto-GOING (matches the mock adapter):**

- Creating an event with `status: "PUBLISHED"` inserts a host `GOING` row. It does not create a save.
- Creating a `DRAFT` does not insert attendance.
- Patching a draft to `PUBLISHED` inserts host `GOING` only when the host has no attendance row. An existing `INTERESTED` or `GOING` row is left unchanged.
- Creating a Move Group sets the creator’s attendance on the parent event to `GOING`, replacing `INTERESTED` when present, and does not clear a save. The creator’s membership role is `CREATOR`.

## 2. Identifiers

Public resource IDs are UUID strings generated by the database (`gen_random_uuid()` / Drizzle `defaultRandom()`). Clients treat them as opaque. Prefixed demo IDs (`evt-…`, `mg-…`, `user-…`, `school-gt`) are mock-only and are not accepted or returned by the API.

`schoolId` on resources is the school’s UUID, not `school-gt`. The seeded Georgia Tech id is `a1111111-1111-4111-8111-111111111111`.

## 3. Viewer context

`request.authUser` is `{ id: string; schoolId: string } | null`.

| Mode | Identity |
| --- | --- |
| `disabled` | Always `null`. Mutations and `requireAuth` fail closed with `UNAUTHENTICATED`. |
| `test` | Header `X-Sesh-Test-User-Id` only, and only when `NODE_ENV` is `development` or `test`. The user row must exist, be `ACTIVE`, and have `primary_school_id`. `schoolId` is that primary school. |
| `managed` | Not implemented. Always `null`. `requireAuth` fails closed. |

Frozen auth rules:

- Startup throws if `AUTH_MODE=test` and `NODE_ENV=production`.
- Test headers are ignored when `AUTH_MODE` is not `test`.
- A present test-user header in `test` mode is an authentication attempt. Unknown, inactive, school-less, or non-UUID values are `401 UNAUTHENTICATED` for that request (including otherwise public routes). A missing header leaves the viewer anonymous.
- `X-Sesh-Test-School-Id` is ignored. It must never set `schoolId`.
- JSON bodies must not carry `hostId`, `creatorId`, or `schoolId`. Create schemas are strict; those fields are `VALIDATION_ERROR`.
- Ownership is the authenticated user id only.

`GET /v1/session` returns `{ "user": { "id", "schoolId" } | null }` and does not require auth. It exists so tests can prove the header was ignored. It is not a product endpoint.

## 4. Visibility

Server policies follow `canViewEvent` / `canViewMoveGroup` in `web/src/lib/permissions/policies.ts`, with the campus and friendship rules in §5 and §6.

| Event | Who can see it |
| --- | --- |
| `CANCELLED` | Nobody. `GET` is `NOT_FOUND`, including the host. |
| `DRAFT` | Host only, same campus. |
| `PUBLIC` + `PUBLISHED` | Anyone scoped to that campus, including guests. |
| `FRIENDS` | Host, or an accepted friend of the host (see §5). |
| `CUSTOM` / `INVITE_ONLY` | Host, or a user listed in `event_audience_members`. |

`customAllowedUserIds` is write-only on create/patch. It is never echoed on `EventView`.

Hidden resources use `NOT_FOUND`, not `FORBIDDEN`, so existence is not leaked. `FORBIDDEN` is for a viewer who is allowed to know the resource exists but cannot perform the action (non-host edit of a visible event, invite-only join, declined re-request, creator trying to leave).

Non-host `PATCH` / `DELETE` of a visible event is `FORBIDDEN`. The same verbs on an event the viewer cannot see are `NOT_FOUND`.

`DELETE /v1/events/:id` soft-cancels (`status = CANCELLED`) and returns `200` `{ "id", "status": "CANCELLED" }`.

Move Group `DISBANDED` is hidden. `GET` is `NOT_FOUND` for everyone, including the owner. `POST …/disband` returns `200` `{ "id", "status": "DISBANDED" }`. There is no disbanded view body.

`GET /v1/events/:id/public-metadata` returns public metadata only for `PUBLISHED` + `PUBLIC`. Anything else is `NOT_FOUND`, with no title or address.

## 5. Friendships

Friendship-based access requires `friendships.status = ACCEPTED`.

`PENDING`, `DECLINED`, and `CANCELLED` grant nothing. The row is undirected once accepted: either requester/addressee order counts (`areConnected` semantics). The frontend `FriendshipGraph.hasEdge` is directed because mock `friendIds` are directed; the database stores one canonical pair, so the API does not model one-way accepted friends.

A block in either direction (`blocks`) cancels friendship access even when an `ACCEPTED` row exists. Blocked users:

- do not satisfy `FRIENDS` event visibility or `MY_NETWORK` group visibility
- do not appear in `friendsGoing`
- do not appear as friend-visible roster identities (they increment `anonymousMemberCount`)
- stay hidden from accepted members as well, except the group creator, who remains visible to anyone who can view the group

Public events stay visible to a blocked viewer. Blocking removes friendship privilege; it does not hide the public campus.

## 6. Cross-campus

Phase 3 scopes every read and write to one school. Cross-campus integrity is enforced in services (the database does not yet composite-FK every relationship).

- Authenticated `schoolId` is `users.primary_school_id` only.
- `GET /v1/events` defaults `schoolId` to that campus. A query `schoolId` that differs is `403 FORBIDDEN` with `details.reason = "CROSS_CAMPUS"`.
- Guests must pass `schoolId`. Missing it is `VALIDATION_ERROR`. Guests only receive `PUBLIC` + `PUBLISHED` rows for that school.
- `GET` by id passes the viewer’s campus (member school, or guest query `schoolId`) into authorization. A resource whose `schoolId` differs is `NOT_FOUND`, including when the caller is the host id on a mismatched campus.
- Event create uses the authenticated campus. Move Group `schoolId` is copied from the parent event and must match the creator’s campus.
- Users are not allowed to operate in a non-primary affiliation in Phase 3.

## 7. Private addresses

`privateAddress` is never a response field. `unlockedPrivateAddress` is omitted when locked (not `null`). `hasPrivateAddress` may be `true`. `privateAddressUnlockHint` follows the frontend hint copy when a private address exists.

Reveal rules match `canViewPrivateAddress`. Guests never receive an exact address, including `PUBLIC_VENUE`.

| `addressPrivacy` | Who gets `unlockedPrivateAddress` |
| --- | --- |
| `PUBLIC_VENUE` | Authenticated viewers who can see the event |
| `RSVP_GOING_ONLY` | Host, `GOING` attendance, or an active Move Group member of that event |
| `APPROVED_GROUP_OR_HOST` | Host or an active Move Group member |
| `HOST_ONLY` | Host only |

No private address stored → do not unlock, even for the host.

## 8. Move Group join modes

`POST /v1/move-groups/:id/join` optional body `{ "note"?: string }`. Success is `200` and the viewer `MoveGroupView` (the group already exists).

| `joinMode` | Result |
| --- | --- |
| `OPEN_JOIN` | Insert an active `MEMBER` row if capacity remains |
| `REQUEST_TO_JOIN` | Insert a `PENDING` request |
| `INVITE_ONLY` | Invited users only; same pending-request insert. Uninvited → `FORBIDDEN` `details.reason = "INVITE_ONLY"` |

Additional attempt results:

| Situation | HTTP |
| --- | --- |
| Cannot view the group or parent event | `NOT_FOUND` |
| Guest | `UNAUTHENTICATED` |
| Already an active member | `CONFLICT` `DUPLICATE_MEMBERSHIP` |
| Pending request already exists | `CONFLICT` `DUPLICATE_REQUEST` |
| Latest relevant request is `DECLINED` | `FORBIDDEN` `JOIN_DECLINED` |
| `active members >= capacity` | `CONFLICT` `CAPACITY_FULL` |
| Creator calls leave | `FORBIDDEN` |
| Non-member calls leave | `NOT_FOUND` |

Capacity checks and membership inserts run in one transaction with a row lock on the group. One remaining seat admits one user. The loser gets `CONFLICT` / `CAPACITY_FULL`.

`joinBlockedReason` on a visible group view uses these strings (guest copy differs from the mock’s demo-switcher text):

- Guest: `Sign in to join or request this Move Group.`
- Pending: `Your join request is awaiting host approval.`
- Declined: `Your previous request for this Move Group was declined.`
- Full: `This Move Group is currently at full capacity.`
- Invite-only and not invited: `This Move Group accepts invited members only.`

Accepted members omit `joinBlockedReason` and set `canRequestOrJoin` to `false`.

## 9. Ownership and member history

- The creator is the only manager (`canManage`). Role `CREATOR` is unique among active members (`left_at IS NULL`).
- Leave and owner-remove set `left_at`. They do not delete the membership row. Removed users disappear from the active roster and can join again unless a `DECLINED` request still blocks them.
- The creator cannot leave and cannot be removed. Those attempts are `FORBIDDEN` (the mock uses `VALIDATION_ERROR`; the API uses `FORBIDDEN`).
- Transfer body is `{ "newOwnerUserId": "<uuid>" }`. The target must be a different active member. Otherwise `FORBIDDEN` with `details.reason = "TRANSFER_TARGET_NOT_MEMBER"`. In one transaction the previous creator becomes `MEMBER` and the target becomes `CREATOR`.
- Approve/decline are owner-only. A missing or non-pending request is `NOT_FOUND`. A non-owner who can see the group gets `FORBIDDEN`.
- Create requires a `PUBLISHED` parent event the creator can view, `capacity` from 2 through 50, and the creator as the sole initial active member.
- Patch cannot set `capacity` below the active member count (`CONFLICT`, no capacity-full reason; that reason is only for join/approve races and full joins).

## 10. DTOs

Responses are viewer projections, not database rows. Field names match `EventView`, `MoveGroupView`, `PublicUserSummary`, and `AdmissionPrice` with these frozen differences:

| Topic | API | Frontend today |
| --- | --- | --- |
| `source` | `"API"` for rows created through HTTP, `"SEED"` for seed rows | `"SEED" \| "LOCAL_DEMO"` |
| `viewerSaved` | Required boolean on `EventView` | Absent; saves live inside `viewerResponse` |
| `viewerResponse` | Attendance only | May be `"SAVED"` in the mock |
| Ids | UUIDs | Prefixed demo strings |
| Locked secrets | Property omitted | `undefined` on the view (same idea) |
| `ownerManagement` | Omitted unless `canManage` | Optional; mock omits it |
| `joinBlockedReason` | Omitted when absent | Optional |

`avatar`, `graduationYear`, `coverImage`, `capacity`, request `note`, and `decidedAt` are omitted when null, not sent as `null`.

Timestamps are ISO 8601 UTC. `admission` is `{ "isFree", "priceLabel"?, "amountUsd"? }`.

Create/patch validation bounds match `web/src/lib/validation/schemas.ts`: event title 3–100, description 10–2000, venue 2–120, public location ≤ 120, private address ≤ 180, price label ≤ 60, event capacity integer 1–50000 or omitted, group name 3–80, note 5–600, group capacity integer 2–50, meetup spot 2–140, http(s) URLs only. `endAt` must be after `startAt`. Paid events require `priceLabel`. Non-`PUBLIC_VENUE` events require `publicDisplayLocation`.

## 11. Errors

Envelope (unchanged):

```json
{
  "error": {
    "code": "CONFLICT",
    "message": "This Move Group is full.",
    "requestId": "…",
    "details": { "reason": "CAPACITY_FULL" }
  }
}
```

Top-level codes stay `VALIDATION_ERROR` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `CONFLICT` (409), `RATE_LIMITED` (429), `INTERNAL_ERROR` (500). `CAPACITY_FULL` is not a top-level code. The mock’s `CAPACITY_FULL` adapter error maps in Phase 4 from `CONFLICT` + `details.reason`.

`details` for `VALIDATION_ERROR` is included only when `NODE_ENV !== "production"`.

`details.reason` for `CONFLICT` and `FORBIDDEN` is always returned, including production, and only when `reason` is one of:

- `CAPACITY_FULL`
- `DUPLICATE_MEMBERSHIP`
- `DUPLICATE_REQUEST`
- `IDEMPOTENCY_KEY_REUSED`
- `INVITE_ONLY`
- `JOIN_DECLINED`
- `CROSS_CAMPUS`
- `TRANSFER_TARGET_NOT_MEMBER`

No other `details` keys are public. No stack traces.

## 12. Cursor pagination

List endpoints (`GET /v1/events`, and Move Group lists when the page can grow) use:

| Query | Rule |
| --- | --- |
| `limit` | Default `20`, maximum `50`. Invalid values are `VALIDATION_ERROR`. |
| `cursor` | Opaque. Absent means the first page. |

```json
{
  "data": [],
  "page": { "nextCursor": null, "limit": 20 }
}
```

`nextCursor` is `null` on the last page. Event order is `startAt` ascending, then `id` ascending.

Server encoding (clients still treat the cursor as opaque): base64url without padding of the UTF-8 JSON object `{"s":"<startAt ISO>","i":"<uuid>"}`. A cursor that does not decode to that object is `VALIDATION_ERROR`.

## 13. Idempotency

`POST /v1/events` and `POST /v1/events/:eventId/move-groups` accept `Idempotency-Key`.

- Length 1–128, no whitespace. Longer or blank keys are `VALIDATION_ERROR`.
- Scope is authenticated user + HTTP method + route template + key.
- The first successful create stores the response and returns **201**.
- The same user, key, and equivalent validated body returns **200** with the stored JSON body and no second row.
- The same key with a different body returns `409 CONFLICT` and `details.reason = "IDEMPOTENCY_KEY_REUSED"`.
- Failed validations and failed creates do not consume the key.
- Concurrent duplicates produce one row; the loser receives the stored **200** replay.
- Retention is 24 hours. After that the key may be used again.
- Storage is shared. The Events agent adds the table below in a migration; Move Groups uses it and does not create a second table.

```text
idempotency_keys
  id uuid primary key default gen_random_uuid()
  user_id uuid not null references users(id)
  method text not null
  route_template text not null
  idempotency_key text not null
  request_hash text not null
  response_status integer not null
  response_body jsonb not null
  created_at timestamptz not null default now()
  unique (user_id, method, route_template, idempotency_key)
```

`request_hash` is SHA-256 of the canonical JSON of the validated DTO (object keys sorted recursively). `route_template` is `POST /v1/events` or `POST /v1/events/:eventId/move-groups`.

Pure functions live in `api/src/modules/authorization/**`. Routes call them and do not copy `policies.ts`.

| Function | Decision |
| --- | --- |
| `areAcceptedFriends` | Accepted, unblocked, either direction |
| `isBlockedPair` | Block in either direction |
| `canViewEvent` | §4–§6 |
| `canEditEvent` | Host, same campus, not cancelled |
| `canRevealAddress` | §7 |
| `canViewMoveGroup` | Parent event visible, group not disbanded, discoverability |
| `canManageGroup` | Active creator, same campus |
| `assessJoin` | §8 |
| `projectRoster` | §5 masking |

`isFullRosterVisible` is true only when the viewer is an active member (or creator) and `anonymousMemberCount` is 0. Blocks can make a member’s roster partial. The frontend flag is true for every accepted member; this is an intentional API difference so the flag matches the payload.
